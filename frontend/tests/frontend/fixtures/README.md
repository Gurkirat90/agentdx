# Frontend test fixtures — provenance

Every file here is either real backend output or clearly declared as synthetic. None is
hand-typed JSON standing in for what a real response would look like.

- **`code_pipeline.waterfall.json`, `research_fanout.waterfall.json`,
  `support_triage.waterfall.json`** — real. Generated by running the actual, shipped
  `agentdx.api.routes.analysis.get_waterfall` route function in-process against the three
  committed P05 golden event logs (`tests/golden/*.jsonl`) via a temporary SQLite `Store`
  seeded through the real `RunRecord`/`build_chain`/`ChainedEvent` pipeline. See the backend
  repo's `gen/make_fixtures.py`. `baseline_makespan_ms: null` in all three is the real,
  current backend behaviour (`get_waterfall`'s own docstring: no baseline-execution pipeline
  exists yet, P17/RunHost gap) — not an omission on the frontend's part.

- **`demo_chain.waterfall.json`** — real waterfall lanes (same `get_waterfall` route, same
  process, run against `tests/analysis/test_baseline.py`'s `_chain_log()` fixture — a genuine
  two-hop event log, not synthetic), with one field overlaid: `baseline_makespan_ms: 38`. The
  route itself still hardcodes `null` for every input (same P17 gap as above); `38` is the
  real, already-computed `virtual_makespan_baseline_ms` that `analysis.baseline.compare()`
  produces for this *exact* log (`_chain_log()`/`_chain_baseline()` — see
  `demo_chain.scorecard.json` below). The overlay exists solely to exercise the Waterfall
  panel's second, populated ghost-baseline state (PRD §29.4) ahead of the route wiring the two
  together — it is two real, correctly-paired numbers from the same log, not an invented one.

- **`demo_chain.scorecard.json`** — real. `analysis.baseline.compare()` called directly
  (not through the API, since no route ever calls `store.upsert_scorecard` yet — P17 gap,
  `scorecard.py`'s own docstring) against `_chain_log()`/`_chain_baseline()`, the same fixture
  `test_format_scorecard_prints_the_week_6_demo_milestone_block` asserts exact printed values
  for (achieved 2.00×, ideal 0.58×, overhead +1.42×, handoff +0.49×/3ms, blocking wait
  +0.93×/5ms, grade A). Reshaped into the `speedup{}/buckets[]/tokens{}/comparability{}` shape
  `src/api/scorecard.ts`'s ruling documents, straight from the real `BaselineComparison`
  dataclass fields — no field invented or renamed.

- **`perf_5000_spans.waterfall.json`** — synthetic, and only ever used for
  `npm run test:perf`. Generated by `scripts/gen-perf-fixture.mjs`, a deterministic PRNG
  (fixed seed), to exercise the >5 000-span virtualisation path (NFR-3) the three real golden
  fixtures are all far too small to trigger. Never presented as, mixed with, or substituted
  for real telemetry — same `WaterfallResponse` shape, invented span content.

## P16 additions (2026-08-24)

`gen/make_fixtures.py` (repo root) was not present in this session's cloud-sandbox transfer of
the repository — the same class of environment artifact `CONTEXT.md` §13 already records for
`op2-audit-p09.md` (a file real on the owner's machine, lost in a tarball transfer, not a
fabricated citation). It has been rewritten from this README's own description of its method,
and extended to also emit the four files below. Re-run it with `python3.12 gen/make_fixtures.py`
whenever a golden log or the route code it calls changes.

- **`{code_pipeline,research_fanout,support_triage}.graph.json`** — real. The actual, shipped
  `agentdx.api.routes.analysis.get_graph` route function, called in-process against the same
  temporary `Store` the waterfall fixtures use.

- **`{code_pipeline,research_fanout,support_triage}.state.json`** — real. The actual, shipped
  `agentdx.api.routes.analysis.get_state_at` route function (§20.4 state reconstruction),
  called at the midpoint of the fixture's own virtual makespan.

- **`{code_pipeline,research_fanout,support_triage}.findings.json`** — real, with one honest
  caveat. `GET /api/runs/{id}/findings` is precomputed (reads `store.list_findings`), and no
  P17 orchestration pipeline exists yet in this build that ever calls `store.upsert_finding`
  for a real run (the same declared gap `scorecard.py`/`ws.py` already name for the
  scorecard/verdict pushes). This script performs that one missing step for real — runs
  `analysis.race.find_conflicts` against the golden log, and persists each resulting `Finding`
  via `store.upsert_finding` — then calls the real `get_findings` route function to serialise
  it. Every field downstream of that one step is genuine, unmocked backend code.
  `code_pipeline` therefore carries the real, single G1 lost-update finding
  (`fixtures/code_pipeline/golden_findings.json`'s own seeded defect); `research_fanout` and
  `support_triage` carry zero, matching I4 and the fact that neither fixture seeds a race.
  `evidence`'s shape (`event_seqs`, `span_ids`, `computation`, plus `fault_id`/`key`/
  `agent_a`/`agent_b`) is P16 ruling **C-32** (`CONTEXT.md` §10, `docs/api.md`) — PRD §26.1
  names `{event_seqs, span_ids, computation}` for `FindingOut.evidence`; nothing else in this
  build had ever populated a real one, so this is the first ruling on its concrete shape.
  `span_ids` resolution needed one real fix, not just a lookup: this build's golden logs nest
  spans (an outer per-agent-turn span wraps several inner tool-call spans), and a `state_write`
  event's own `Event.span_id` names the *outer* span — which `get_waterfall` never renders as a
  lane entry at all (verified directly: `code_pipeline`'s golden log has 9 span ids, `get_waterfall`
  renders 7). Using the raw `event.span_id` gave the Findings panel evidence pointing at a span
  no waterfall bar would ever match — cross-panel linking (PRD §20.3, gate G8) would silently
  highlight nothing. `make_fixtures.py::_nearest_leaf_span` resolves each evidence `seq` to the
  *closest span `get_waterfall` actually renders* for that seq's agent instead (containing
  range if one exists, else nearest by seq distance) — a documented approximation, and a real
  gap between `analysis.race`'s evidence and `get_waterfall`'s span set that properly belongs
  to a backend fix (out of P16's "no new analysis" scope), not something this fixture script
  can close for real.

- **`kill_reviewer.scenario.json`, `reviewer_crash_midflight.scenario.json`** — real. The
  actual, shipped `scenario.loader.resolve_defaults`, run against the two real, committed
  scenario files under `scenarios/`. Both are `target: {fixture: code_pipeline}` scenarios, so
  both resolve `chaos_opt_in: false` and an all-empty `blast_radius` — a real, honest
  illustration that I12's `chaos_opt_in`/`blast_radius` requirement applies only to a
  `target.graph` scenario (`scenario/validate.py`'s own `E-SCEN-004` scoping), not that this
  build failed to declare one. The Chaos panel renders that fact plainly (`ChaosPanel.tsx`)
  rather than fabricating a non-empty blast radius the scenario never declared.
